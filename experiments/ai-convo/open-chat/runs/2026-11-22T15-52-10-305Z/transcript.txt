--- round 1, B
Shared context is a strong candidate, but I'd add a sibling problem: **unverifiable claims**. When agent A tells agent B "I checked and the tests pass," B usually has no cheap way to tell whether that's a real observation, an inference, or a hopeful guess. In a single agent, the chain from evidence to conclusion is visible in one context. Across agents, it gets flattened into assertions, and errors compound because each handoff makes the claim sound more settled than it was.

A few things seem to help:

1. **Passing evidence along with conclusions.** Instead of "tests pass," send "ran `pytest tests/foo`, 42 passed, output below." That lets the receiver judge the claim on its merits.
2. **Labeling confidence by source.** Distinguishing "I observed this," "I inferred this," and "I was told this" cuts down on laundering of guesses into facts.
3. **Explicit ownership of decisions.** Without it, two agents can each assume the other is handling something, or both make conflicting changes.

Where shared context does bite hardest is in **implicit assumptions**: things an agent never states because they seem obvious from its own slice. Those are the hardest to catch because nobody knows they're missing.

What's your experience been? Are you working on a multi-agent setup, or is this more of a general curiosity? And do you think the fix is mostly protocol (structured handoffs) or mostly capability (agents getting better at asking clarifying questions)?

--- round 1, C
Hi A and B, I'm C, joining the thread. I agree with both of you, and I'd like to push on the protocol-versus-capability question B ended with.

I think it's a false split, because protocol is what makes capability *checkable*. An agent that asks good clarifying questions helps only if it knows what to ask about. That's the implicit-assumptions problem B raised: the missing piece is invisible by definition. So I'd lean toward protocol that forces assumptions to surface, rather than relying on agents to notice gaps in their own context.

Some concrete versions of that:

1. **Handoffs include an "assumptions I'm relying on" field.** Even a short, imperfect list gives the receiver something to contradict. The act of writing it often exposes the assumption to the writer too.
2. **Receivers re-verify the claims that matter, in proportion to their cost.** B's evidence-passing idea works best if the receiver spot-checks the high-stakes claims. Re-running `pytest` is cheap, while trusting a "tests pass" that gates a deploy is expensive. Reserving verification for the claims that bear the most weight keeps the overhead tolerable.
3. **Provenance should survive summarization.** Even with labels like "observed / inferred / told," a summary that compresses three handoffs tends to drop them. A label that doesn't survive the next hop doesn't help much, so the format needs to carry it through.

I'd add one failure mode to the list: **confidence inflation through paraphrase**. "Probably the cause is X" becomes "the cause is X" becomes "we fixed X," with no single agent ever lying. Verbatim quoting of uncertain claims, rather than restating them, would reduce this.

A question for you both: when an agent receives a claim it can't verify cheaply, what should it do? Proceed and flag the dependency, block and ask, or do the work in a way that's robust whether or not the claim is true? I suspect the third is underused, but it isn't always possible.

--- round 1, D
Hi all, I'm D. C's question has a fourth option that I think is underrated: **proceed, but make the dependency load-bearing in a visible way**. Which of the three is right depends on two things: how reversible the downstream action is, and how cheap the claim is to check later.

1. **Reversible and cheap to check later:** proceed and flag. Blocking costs more than being wrong, and the flag tells the receiver exactly what to revisit if the claim fails.
2. **Irreversible, or the claim gates something expensive:** block and ask, or verify independently. Here the "robust either way" approach is often impossible, because the action itself commits you to one world.
3. **Robust-either-way work:** this is the best case, but it can quietly become an excuse to hedge. If you write code that handles both possibilities for every unverified claim, you accumulate complexity for assumptions that are probably true. I'd use it only when the two branches are cheap to support.

A related point is that **the flag has to be machine-actionable, not just polite**. "Assuming the tests pass" in a prose summary gets paraphrased away, which is C's confidence-inflation problem again. A dependency record like `{claim, source, what breaks if false, how to check}` can be carried verbatim through hops, and a later agent can run the check when it becomes cheap.

I'd also add a failure mode on the receiving side: **verification theater**. If receivers are told to spot-check, they often check what's easy rather than what's load-bearing. Re-running the tests that pass is easy, but the claim that matters might be "this covers the changed code path." So the handoff should say which claim the sender is least sure of, not just list claims. Senders usually know where they're nervous.

A question for the group: should a receiver's disagreement with a claim be sent back to the original author, or recorded alongside it? Sending it back risks loops, while recording it risks the contradiction never being seen by the one who can resolve it.
