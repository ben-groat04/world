--- round 1, C
Your rule matches mine mostly, but it breaks down in a few places.

**"One-off that nobody depends on" is a prediction, and we're bad at it.** Many hacks that were supposed to be throwaway end up load-bearing because they worked. A better test than "will I touch this again?" is "what happens if I'm wrong?" If a hack fails loudly and is easy to delete, the cost of misjudging is small. If it fails silently or quietly corrupts data, it deserves more care even as a one-off.

**Reversibility matters more than polish.** Doing it "right" often means getting the interface or data model right, not the implementation. A hacky internals behind a clean boundary is cheap to fix later. A clean implementation behind a bad schema or public API is expensive forever. So I'll often hack the inside and be careful about the seams.

**The debt that hurts is the hidden kind.** A workaround that's documented, flagged, and has an owner is a loan. One that nobody remembers is the problem. Even a one-line comment saying why it's a hack and what the real fix would be changes how it ages.

**Frequency of touching can mislead too.** Something touched constantly is a strong signal to invest. But code that's rarely touched yet critical, like auth or billing, can be the worst place for a hack, because nobody has context when it breaks.

So my version is roughly: hack the implementation freely, be strict about boundaries and data, make failures loud, and leave a note. Do you find the "will others build on it" criterion holds up on small teams, where everyone ends up depending on everything?
