# open-chat

Claude agents (Haiku by default) chatting freely, with almost no instructions. Everything for it lives in this folder. It needs Node 22+ and the `claude` CLI, signed in. No API key is needed.

## Run a conversation
From this folder:

```
node run.mjs                          # 4 people (a generated cast), open chat, up to 120 messages
TOPIC="..." node run.mjs              # the first person has this on their mind and opens with it (it is in the opener's first turn only, not in any system prompt)
PEOPLE=6 node run.mjs                 # 2-8 people
MODEL=sonnet node run.mjs             # default haiku
ORACLE=1 node run.mjs                 # agents can write "@claude ..." to ask Claude, which searches the web and reads pages (ORACLE_MODEL, default sonnet); the answer goes only to the asker, as "(Claude replied to you:)" at their next check-in
REACT=0 node run.mjs                   # reactions are on by default (an agent replies "REACT 👍" to put an emoji on the latest message from someone else, meant for a message a reaction answers; no notification; everyone sees a count under the message); 0 turns them off
# (the cast is not optional: names, roles, lives, sleeping hours and how each person texts all come from the casting call. Life moves on at unprompted looks: once that person's look time has come (6 in-story hours x a per-refresh factor of 0.6-1.8 after their last refresh), what has happened to them since is generated and shown at that look in a block marked as not on their phone, before the chat)
EFFORT=default node run.mjs              # omit the --effort flag (default is low) to compare
GEN_ONLY=1 node run.mjs 1 "brief"        # only run the casting call, write the run folder, exit (read the casts: roles, names, registers)
LINES_FROM=runs/<folder> node run.mjs    # reuse that run's cast row (arms of one seed share a world; same PEOPLE; older runs have no cast row)
SECRETS='{"Tom":"..."}' node run.mjs  # a private line for chosen people ("Only you know this, at least at first: ..."), keyed by the viewer form's default names Maya, Tom, Jo, Sam, Priya, Dan, Ellie, Kofi: the secret for the default name of slot k goes to person k, whatever the cast calls them (default names inside a secret or topic are replaced the same way)
START=2026-12-01T19:00 node run.mjs   # in-story start time (default 19:00 today)
DAYS=2 node run.mjs                   # in-story days before the run ends (default 3)
node run.mjs 60 "custom brief"        # message limit, brief override
```

### Paired batches (batch.mjs)
Arms are compared on the same casts, not on separate draws (round 18: per-window scores vary ~1.6 points between casts, so unpaired arms of 6-9 runs can only show differences over ~1.8 points).
```
node batch.mjs gen b19 --seeds 3                      # one casting call (GEN_ONLY) per scenario x seed; batches/b19/manifest.json (scenario, seed, START, cast folder)
node batch.mjs run b19 --arm BASE --arm NEW --code ../open-chat-new --env REACT=1   # every arm on every cast (LINES_FROM, same START); --code: a copy of this folder with the changed code
node batch.mjs list b19                               # batches/b19/list.txt: "BASE-T11 <run folder>" lines, as eval-prep reads
```
`--scenarios file.json` replaces the default nine (T1-T6, U1-U3 of earlier rounds) with fresh briefs ({"Name": {people, brief?, topic?, days?, messages?, start?: "monday", secrets?, env?}}): swap in new ones each round so nothing is tuned to the same nine. `--only T1,U2`, `--seed 1` and `--conc 6` narrow or pace a batch. Labels are `ARM-<scenario><seed>` (arm letters, digits and `_` only). Then `node eval-prep.mjs batches/b19/list.txt <out dir>`.

Each run writes `runs/<timestamp>/transcript.txt`, plus `log.jsonl`, which has a row per posted message, per PASS and per reaction (`react`, `to`), plus oracle rows and the end row. Runs take a few minutes, so run them in the background.

### How it works
- **The agents:** each one is a fresh `claude -p` call with `--system-prompt` set to the relay note plus "You are <name> (<age, gender, role>)." and the brief (the chat, the shared setting, how you stand to the others, your life, your secret if any, and one sentence on how often you message unprompted, what you are like; no typing style, no example texts). They get no tools (with `WebFetch` they kept trying to look things up and then explained they couldn't), a temp working folder and a fresh config folder. That keeps Claude Code's coding prompt, CLAUDE.md and account details out. The CLI still adds a short environment note, and the system prompt tells them to ignore it. That line is left out of the logs. Agent and generator calls use `--effort low` (`EFFORT=<level>` overrides it, `EFFORT=default` omits the flag), the rewrite pass `--effort medium` (about 1 in 20 rewrite calls at low did not think, and weighed its rules in the answer, which then posted), and `--system-prompt-snapshot off` (hard-coded design settings), and replies are capped at 4000 tokens. A turn where the CLI injected its "Output token limit hit" continuation is a failed turn: not posted, logged `{failed: 'continuation'}`, a PASS for scheduling. So is an API refusal (`[reasoning_extraction]`, "can't help with this"), of an agent call or of the rewrite pass: logged `{failed: 'refusal', error, draft}` (the draft when it was the rewrite that was refused), not posted, a PASS for scheduling; any other error still stops the run. `CLAUDE_CODE_DISABLE_ATTACHMENTS=1` drops the CLI's per-turn "<total_tokens>…tokens left" reminder; the CLI's SDK identity line, the model-identity line, the date and the environment note's curl/untrusted-file advice cannot be turned off (the first is chosen by the CLI when run non-interactively, the rest are hard-coded in it). Each run keeps its temp config folder, and the first log row `{config_dir}` names it (the CLI's session files show what the models saw).
- **Clock:** there are no turns and no rounds. Each agent has its own next check-in time, and the loop takes the earliest pending event (a check-in, a message finishing being typed, an `@claude` answer arriving) and moves the in-story clock to it. At a check-in the agent sees its phone, the life events, the phone screen (the last 30 messages before the new ones, a "(new)" line, and what is new), with its own messages marked "(you)" (the whole chat on its first look), and last of all the time and when it last looked ("(Jo's phone, Wed 17:03. You last looked Wed 12:10.)"), next to the point of reply. Its reply is posted when finished: check-in time + time to read the new messages (238 words/min, Brysbaert 2019, non-fiction) + time to type it. Each agent's phone typing speed is drawn once from a normal with mean 36.17 and SD 13.22 words/min (Palin et al., MobileHCI 2019; a copy-typing task), floored at 10 (a design choice). A reply with blank lines becomes several messages, each posted after its own typing time (a part ending with `:`, a list, or a lone `---` stays joined with its neighbouring part). Messages that arrive while someone types are seen at their next check-in, so replies can cross, and anyone can post twice in a row.
- **Check-ins:** whenever a message posts (Claude's answers too), an agent with nothing unread gets one check-in after a log-normal delay (median 6.15 min, a quarter within 60 s; Pielot et al., CHI 2014) drawn at the first unread message; later messages don't reschedule it. An agent mid-reply is notified once it has posted, if something is unread. Claude's private answer also counts as unread for the asker.
- **Seeing messages while typing:** just before a reply's first message posts, if others posted since the check-in, the agent is called once more and shown the phone screen with them, followed by its unsent draft under a header like the others ("— Tom (you, not sent yet)"), and answers `SEND` (post the draft unchanged), `PASS` (send nothing) or a message to send instead (the prompt ends: "Your message isn't sent yet; nobody has seen it. SEND sends it, PASS deletes it, or type what you send instead.", `RECHECK_END` in `prompts.mjs`). The separate menu is kept: without `SEND` an unchanged draft would have to be retyped. Every draft is re-checked when something crossed; spotting that a crossed message is not a reply to the same thing would need another model call, so it isn't done. That answer replaces the draft; a changed one is typed again, a `SEND` posts on schedule. The log row has `draft` and `recheck`; a dropped draft is a PASS row with `draft`. Spontaneous check-ins with nothing new (so someone can open a new conversation the next day) come 30 to 600 minutes after a PASS or a finished reply (unsourced design parameter). Agents don't check in while asleep: the sleep window differs a little per agent (around 22:30-24:00 to 06:00-08:00, unsourced, TODO: source), and a check-in inside it moves to the agent's wake time. The first person opens at the start time; the others first look within the first two hours.
- **Reactions:** on by default (`REACT=0` turns them off): a reply of `REACT` and an emoji attaches to the latest message from someone else, notifies nobody and counts as a PASS. The relay note says to use it only on a message a reaction answers ; the cast no longer says how often a person reacts (round 19: with the clause in, reactions replaced replies; replayed without it, REACT fell from 47% to 25% of group notification turns), only the note's "use it only on a message that a reaction answers". It only counts if that message was first shown at this check-in; a `REACT` with nothing new is logged as a PASS. Everyone sees reactions as a count under the message ("(👍 2)"), not as lines naming who sent what emoji, so there is nothing to copy.
- **The cast (casting call):** one call writes a coherent cast from the brief, however short ("me and my mum", "five-a-side team", "my ex"): per person a first name that fits the place, culture and age, "age, gender, role" (every role in the brief goes to exactly one person; a brief from one side, "my ex", makes that person person 1), how they stand to each other person, where they live, occupation and their week (the job is one part of it), what they are like (`like`, two short sentences, second person: temperament and sense of humour, what they have opinions about or get enthusiastic about, how they get on with each of the others; round 19, agent only: the cast gave each person a job, a week and a typing style and nothing else, so every message was logistics or Day news), usual sleeping hours, how often they message it unprompted (`texts`, one sentence, frequency only: the reaction clause was dropped in round 19; the agent sees it), how they type (`style`, 1-2 plain sentences: capitals, punctuation, emoji, length, abbreviations; used only by the rewrite pass) and six example texts (at least half plain); and once a shared setting. A group of one cohort is asked to share a register; family members can differ. The place is drawn at random from 12 the model lists privately (the setting call once put 11 of 14 runs in Leeds). The names, roles and texting styles are not fixed lists and no longer come from `styles.mjs` (removed). Log: the first cast row `{private_lines (the life lines), setting, names, cast: {name: {who, knows, like, texts, style, ex}}, sleep, opener, situation, topic}`. If the call misses a field it retries once, then the run fails. `LINES_FROM=<run folder>` loads that row; `GEN_ONLY=1` only generates and exits. Internally people are slots (the first is slot 1, the opener and topic holder); the viewer form's default names only say which slot a secret belongs to.
- **Life events:** at an unprompted look once `REFRESH_HOURS` (6, a design parameter) times a per-refresh factor of 0.6-1.8 has passed since a person's last refresh, one call generates what has happened to them since (no topic or secrets): from the identity, the weekday, date and time, the previous events as background, and everyone's messages since then (asking how the things the person said they'd do went). It gives the "Day:" first (two or three short sentences, no mention of the chat or messages; if something happened that connects to these people or what they share, it is the first sentence; if something arranged in the chat involving the person was due by now, it says whether they were there and how it went), then a "Small thing:" line that copies that first sentence or says "nothing" (it feeds the no-repeat list), then "Next:" (round 19), the day and time ("Sat 17:10") the person will next have the phone in hand with a moment to spare, given their day, their sleeping hours and what was arranged. `Next` sets the time of that person's next unprompted look (`parseNext` in `prompts.mjs`; at least 10-90 minutes after now; log row `next`); it replaces the random 0.6-1.8 x `REFRESH_HOURS` after the last refresh (only a person's first refresh still uses that), which left nobody looking around an agreed time and put 21% of posts at 06:00-07:59. The agent never sees the reason for a look. Written the other way round (Small thing first) the Day left it out in about half of the refreshes. The day opens that check-in's user turn in a block "[Not on your phone: your own day, which you lived yourself. Nobody sent you this.]" followed by "[The chat on your screen:]" (log row `private_lines: {name: events}`, `day`, `at`, `small`), not the system prompt. Events are asked to be ordinary and mostly neutral or good, no emergencies, no continuing old problems. Every refresh look is a turn, even when the Small thing is "nothing" (it only feeds the no-repeat list); a look with no refresh and nothing new in the chat is skipped. The Day is told that the person's life went on since the last refresh: whatever they were in the middle of or waiting on is over, and it says how it ended; the first sentence can also be how something they said in the chat they would do turned out. Apart from that outcome, nothing in the day comes from the chat (no jokes, objects, places or details from it). The relay note says the same of the time between looks. It also says that people you are with in person you talk to there, not in the chat. There is no reason or want for the look: nobody is told what to bring up (a hidden director made the agents chase things already settled, re-ask, and run six scheduling threads at once). The agent sees the whole screen and decides; an unanswered question is just visible. Only the opener's first look has a cue: the topic, or the casting call's "opens with" line. When everyone else is inside their sleeping hours the header adds "The others are probably asleep." (design: the plain fact, so a 04:00 look is seen as one).
- **Attachments:** a reply line `[file: name.ext]`, `[photo]`, `[photo: what it shows]` or `[link: what it is]` posts as its own attachment message (no real files; log row `attachment: true`).
- **Reading a reply:** the final non-empty line of a reply decides (PASS, REACT plus an emoji, SEND): narration before it is not a message; a line that is only an HTML-style tag (e.g. `</br>`) is ignored when finding it. There is no memory between calls: each agent gets its brief, the last 30 chat messages (its own as posted) and its previous three event paragraphs. Older runs differ: before 2026-11-22 17:40 each agent was one long-lived process, and until round 17 the default arm resumed forked saved sessions.
- **Ending:** at `MESSAGES` posted messages (Claude's private answers do not count; replies already being typed still post, no new check-ins start), or when the in-story clock passes the start plus `DAYS` days (default 3). The last row of `log.jsonl` is `{end: 'limit'|'date', at}`.
- **Voice is applied once:** the agent writes content (relay note, cast, its own "How you text" sentences, no examples); the rewrite pass is the only voice step (below). Earlier runs gave the style card to both and the markers ("... . 🙂", "um", "hun ❤️") were stamped twice.
- **Rewrite pass:** every reply, and every rewritten re-check answer, goes through `polish()` before it is posted: one stateless call with the person's style description (the casting call's `style` line: capitals, punctuation, emoji, length, abbreviations), their example texts, their last 4 posted messages and the last 12 chat messages rewrites the draft as that person would type it, or answers `DROP` (a PASS). It is told their habits show in some texts, not every one, not to reuse an opener, phrase or emoji from their last texts in this chat or the last messages (one rule), to cut filler only (thanks, sympathy formulas, greetings, sign-offs, what the chat already says) and keep what the draft adds (a decision, a yes or no, an offer, a time, what they will do), and to use no names or @ unless it would be unclear who is meant. Log rows: `raw` (the agent's own reply), `polish` (the call's usage), `polishDrop: true` on a DROPped reply (a PASS row); `draft` is still the text before the re-check, now the polished one.

## Viewer (claude.ai Artifact)
- **`node viewer/build.mjs`** writes `viewer/runs.json`. That holds every run since 2026-11-23 07:12 UTC (`SINCE` in build.mjs; earlier ones were tests, cleared from the viewer at the user's request). Runs from the cast version log the topic and situation in the cast row; the viewer's Start form still sends situation, topic, people and secrets by the default names.
- **`viewer/index.html`** plays the runs back. Publish it with the Artifact tool:
  - `file_path`: `viewer/index.html`
  - `files`: `{"runs.json": "<absolute path>/viewer/runs.json"}`
  - `capabilities`: `{"comments": {}, "db": {}}`
  - Don't republish after a run: the run reaches the page through the database (below), and a republish reloads every open view back to the top. Republish only when the page itself changes. That publish also folds the database runs into `runs.json`.

### Operating it from a Claude session (the session that publishes the page)
1. **Start requests.** The page's Start button sends this session a comment that begins `START RUN`, with lines `model:`, `people:`, `messages:`, `oracle: yes|no`, `topic: <text or (none)>` and `secrets: <JSON>`. To act on one:
   - Run `run.mjs` in the background with the matching env vars: `MODEL`, `PEOPLE`, `MESSAGES`, `ORACLE=1`, `TOPIC`, `SECRETS`.
   - Reply in the comment thread, then resolve it when the run ends.
2. **Database runs.** The page shows each new run, live and after it ends, from the artifact's database:
   - collection `live_runs`: doc id `<runId>`, run meta plus `status: running|done`
   - collection `live_turns`: doc id `<runId>-<4-digit i>`, fields `{run, i, who, text, at, clock?, oracle?}`

   A run that is also in the published `runs.json` is shown from there.

   While a run goes, watch its `log.jsonl` with a Monitor that checks every second and prints a line whenever the posted count grows, and also when the run process exits. Act on each event straight away, so messages reach the page a few seconds after they are posted (events that pile up while a write is in flight go out together in the next batch). On each event:
   - Run `node viewer/live.mjs <runId> <outDir>`. It writes `run.json` plus one `turn-XXXX.json` for each turn not yet sent, and prints the new turn files.
   - Write them with one `ArtifactData` batch: `set` `live_runs/<runId>` from `run.json`, and `set` each turn into `live_turns`. If a doc already exists, pin the write to its `version`.

   When the run ends, do the same with `done` as the third argument, then rebuild `runs.json` and commit it.

The artifact and its database belong to whoever publishes it. A new account publishes its own copy, and only that session receives its Start requests.

### Starting a run with the writer (live, W4)
`writer.mjs --live` is the single writer run from the Start form. It writes one chat day by day (day N+1 is written while day N plays) and releases the messages on the story clock. The session that owns the page runs one command per START RUN comment and mirrors what it prints into the database:
1. Write `spec.json` from the comment: `{"situation": "<situation text, or omit>", "topic": "<topic or omit>", "people": <n>, "secrets": {"Maya": "..."}, "model": "haiku|sonnet", "oracle": true|false, "days": 2}`. `secrets` and `topic` use the form's default names (Maya, Tom, Jo, Sam, Priya, Dan, Ellie, Kofi); the writer maps them to the cast's names. `start` (`2026-11-23T19:00`, story time) is optional: the default is the current local time. `messages` is not used (the run lasts `days` + 1 waking days, default 3 chunks).
2. Run, in the background: `node writer.mjs --live <spec.json> --out <outDir> [--speed 60]`. `--speed` is story seconds per real second (design parameter, default 60: one story minute per second; a quiet 8-hour stretch takes 8 minutes). `--oracle` also works as a flag; `"oracle": true` in the spec turns it on.
3. It prints one line per file written under `<outDir>` (default `writer-runs/<timestamp>/export`): `RUN <outDir>/run.json` (after casting, status `running`), `TURN <outDir>/turn-XXXX.json` (each turn at its story time; day markers are `Clock` turns; an `@claude` answer is a turn with `who: "Claude"`, `oracle: true`) and `DONE <outDir>/run.json` (status `done`, `ended: "end date"`). Watch that output (Monitor) and on each line write to the artifact database, as for `viewer/live.mjs`: `RUN`/`DONE` set `live_runs/<run id>` from `run.json` (its `id` field); `TURN` sets `live_turns/<run id>-<4-digit i>` from the turn file (`run`, `i`, `who`, `text`, `at`, `clock?`, `oracle?`). Batch lines that arrive together into one `ArtifactData` write. Reply in the comment thread, and resolve it at `DONE`. The mirroring (Monitor plus `ArtifactData` writes) is done by a Haiku agent, not by the orchestrating session; the orchestrator starts the run and handles the comment thread.
4. The run folder `writer-runs/<timestamp>/live/{log.jsonl, transcript.txt}` is rewritten after every day. `node viewer/build.mjs` includes such runs (`live: true` in the log header) in `runs.json` afterwards; republish the page only when the page changes.

A failed day leaves the run `done` with `ended: "message limit"` (the viewer shows "Cut off"); `rejects.txt` in the writer's timestamp folder holds any chunk text that was rejected.

## Single writer (writer.mjs)
One Haiku call writes each waking day of a chat from a generated cast (see `ITERATIONS.md` W1-W4 for the rounds, `notes/diagnoses/w4-diagnosis.md` for the current plan). `node writer.mjs --gen briefs.json [--days 2] [--conc 3] [--model haiku|sonnet] [--oracle]` casts and writes (briefs: `[{"label","people","brief","topic?","secrets?","start?"}]`); `node writer.mjs <list> --prefix X` rewrites the chats of an existing list (their casts and start times; label `ARM-scenario`); `--live` is above. Output: `writer-runs/<timestamp>/<label>/{log.jsonl, transcript.txt}`, `list.txt`, and `rejects.txt` for chunks rejected by the stamp check.
- With `--oracle`, a message starting `@claude` ends the chunk; Sonnet with web search (`ORACLE_MODEL`) answers, the answer is posted as `Claude` stamped after the real call time, and the same day resumes from there.
- `w4-checks/`: `metrics.mjs` (W3's metrics, oracle rows left out), `cohab.mjs` (evening quick replies between people who live together), `big.mjs` (groups of 5+). `cut.mjs` and `cut-replay.mjs` are the delete-only pass and its replay (it lost its blind check, so the writer does not use it). `judge.mjs <eval dir>` runs the Sonnet judges over the judge folders `eval-prep.mjs` cut (`PAIR=1` keeps every window of one cast away from the same judge).

## Judging (eval-prep.mjs)
`node eval-prep.mjs <list> <out dir> [real-text files...]` cuts blind windows by in-story time, not message count (round 19): A = the run's first 36 in-story hours from its first message, at most 40 messages; B = the next 36 hours, at most 40. A window is judged when it holds at least 8 messages, so runs that stop talking after the topic is settled are judged (and show their silence) instead of dropping out. `<out>/runs.tsv` records each run's message count, the counts in A and B and its status (dead = 0 messages, short = fewer than 8 in A, A-only, full) and `--tally` prints the counts per arm with the judged share next to the scores. A message's reactions appear as a count under it ("(👍 2, 😂 1)"), as a phone screen shows them, not as timestamped "X reacted" lines. `<out>/judge-note.txt` holds the plain fact to tell every judge with the neutral ask: each file is an excerpt from a longer chat. Optional second question, asked after the score so the score stays neutral: `<out>/judge-detect.txt` ("how likely, 0-100, is it that this chat is between real people texting?"); put the number as a third column in `scores.tsv` (`id<TAB>score<TAB>p_real`) and the tally prints its mean per group. Real chat files given after the out dir (blocks `--- Sun 19:41`, first 40 used) are mixed in blind as arm REAL, window `real`. `baseline.mjs <list>` writes one-call whole chats for the casts of a list, as runs eval-prep reads (below).

## Cheap checks (replay.mjs) and run metrics
- `node replay.mjs turns <run>... [--kind opener|look|notif|all] [--logged quiet|any] [--n 5] [--rows 3,7]` re-issues logged check-in turns (the logged `user` and brief, today's system-prompt shape: no wants, no topic, no examples; old reaction lines become counts) with the current relay note (`prompts.mjs`), N samples each, then the current polish; prints per turn the post rate, REACT rate and what is left after polish, the totals and the REACT emoji used. `look` turns have the old "(You've opened the chat to ...)" line dropped. Stateful runs resumed a saved session per look; a replay is a fresh call with the logged screen, so it tests the prompts, not the memory.
- `node replay.mjs refresh <run>... [--rows i,j] [--n 5]` re-issues logged daily-refresh calls with the current refresh prompt (`dayAsk` in `prompts.mjs`) and prints the Days and the share whose Small thing is "nothing". `node replay.mjs quiet <run>... [--n 3]` puts each refresh look that older runs skipped (Small thing "nothing", nothing new in the chat) in front of that person's screen with the logged Day and replays it as a turn: post rate and the posts. `turns` moves an older run's leading clock line to the end of the screen, as today's runs send it.
- - `node replay.mjs recheck <run>...` (round 19) re-issues the logged re-check turns twice, with the logged closing line and today's, and counts SEND, PASS, rewritten answers and rewritten answers that comment on the draft itself. `turns` also takes `--like <file.json>` (adds a generated "What you're like" line to casts that lack one, written to the file so both arms use the same lines), `--cut-react` (the "How you text" sentence with its reaction clause removed by a model call) and `--max k` (at most k turns per run, evenly spaced), and prints post, REACT and "?" rates per chat type (group or 1:1). `refresh` prints each sample's `Next` with its distance from now and the hour histogram of `Next` against the logged look hours.
- `node replay.mjs polish <run>...` re-polishes the logged `raw` drafts (with the person's last 4 posted texts) and counts instruction leaks (`/rewrit|draft|wait,|I need to|opener/i`), emoji repeated from the person's last 4 posts, emoji, slang and new words not in the raw, against the polish that ran then; and per person with 4+ posts the share of posts carrying their most frequent habit marker (ending "...", "um"/"hmm", a final emoji, a final "x", "!!", leading lowercase, an abbreviation) and the share naming someone, then and now.
- Round 18 tooling: `replay.mjs polish` takes `--rows` (log row indexes) and `--rep k` (each draft k times), reads `POLISH_EFFORT` (default medium, as the run) and `POLISH_NOECHO=1` (the echo-cut sentence removed from the polish prompt), and prints how many polish calls thought. `replay.mjs refresh` prints how many Days contain a chat word (4+ letters, not in the person's life line) and `turns` takes `STRIP_COUNTS=1` (reaction counts removed from the screen). To compare with the previous prompts, run a copy of the folder with the older `prompts.mjs` (a `runs` symlink to the real one).
- `score.mjs` machine metrics, free on every run (round 19): `perTurn` (posted messages per turn: 0.53, 0.45, 0.39, 0.35 pooled over the rounds 7-10 batches), `reactPer` (reaction rows per posted message: 0.29, 0.37, 0.65, 0.64), `qAny` (share of messages containing a "?"), `wake90` (share posted from 30 min before to 90 min after the writer's wake time). Pooled over a batch they give the numbers above; the MEAN row is a mean of per-run values.
- `score.mjs` also reports per run: `perDay`, `starts` (posts at least 2 h after the previous one, per day), `opener`, the PASS share by situation (`passFirst`, `passEvEmpty`, `passEvQuiet`, `passEvNew`, `passNotif`), `dropRate`, and the rewrite's added tokens (`addStyle`: emoji + slang not in the raw; `addAll`: all new tokens).

## One-call baseline (baseline.mjs)
`node baseline.mjs <list>` (round 19, a diagnostic, not part of the pipeline) writes, for each cast of a list of runs, the first 36 hours of the chat in a single Haiku call (cast, setting, topic or opener in; the format "--- Mon 19:41, Name", reactions as "(👍 2)" lines under a message) and saves each as a run folder under `baselines/<timestamp>/` (`ONE-<scenario+seed>`, `log.jsonl` with the cast row and one row per message, `transcript.txt`) plus a `list.txt`. Concatenate it with the multi-agent list and give both to `eval-prep.mjs` to judge them blind on the same casts: if the one-call chats score as well, the agent machinery is not buying realism.
